# DevDigest — repo map

Local-first AI PR review. 4 standalone packages, no workspace — cross-package
contracts are shared by vendoring `vendor/shared` into each package that needs
it (not published, not npm-linked).

## Stack

Node ≥22 · pnpm ≥10 · Fastify · Next.js 15 · Drizzle/Postgres (pgvector) ·
Docker (Postgres only — API and web run on the host).

## Where things live

| Package | Role | Read when |
|---|---|---|
| [server/](server/) | Fastify API + DB + LLM adapters + repo-intel | touching API routes, DB schema, LLM adapters, repo-intel |
| [client/](client/) | Next.js studio UI | touching pages, components, hooks |
| [reviewer-core/](reviewer-core/) | diff → prompt → LLM → findings engine | touching review logic, grounding, prompt assembly |

- Cross-package findings from earlier sessions: read [INSIGHTS.md](INSIGHTS.md).

## Non-default conventions

- No monorepo workspace. `server/src/vendor/shared` and
  `client/src/vendor/shared` are the same contracts package, vendored into
  both — see each package's AGENTS.md before editing either copy.
- `server/` does not run DB migrations on boot — always `pnpm db:migrate`
  manually after pulling schema changes.

## Naming conventions

- **Files/dirs, server (`server/src/`)**: kebab-case, one word per concept
  (`repo-intel/`, `run-executor.ts`). Each feature is a module folder under
  `src/modules/<name>/` split into `routes.ts` → `service.ts` →
  `repository.ts` — don't collapse the split (see `server/AGENTS.md`).
- **Files/dirs, client (`client/src/`)**: route/page files follow Next.js
  conventions (`page.tsx`, `layout.tsx`, lowercase). Feature components live
  one-per-folder under `_components/<ComponentName>/` — the **folder and the
  component are PascalCase** (`PRRow/PRRow.tsx`, `FindingsSummary/
  FindingsSummary.tsx`), with lowercase sibling files in the same folder
  (`helpers.ts`, `styles.ts`, `constants.ts`, `index.ts` re-exporting the
  component). Non-component lib files are kebab-case/lowercase
  (`github-urls.ts`, `repo-context.tsx`).
- **Tests**: co-located next to what they test, same base name —
  `<Name>.test.tsx` (client) / `<name>.test.ts` (server unit) /
  `<name>.it.test.ts` (server integration, Testcontainers-backed — the `.it.`
  infix is how `test/` distinguishes the two).
- **Code identifiers**: `camelCase` for variables/functions, `PascalCase` for
  React components/TS types/Zod schema constants (`PrMeta`, `SeverityCounts`).
- **Database**: Drizzle table/column definitions are `camelCase` in TS
  (`prId`, `costUsd`) mapped to `snake_case` in Postgres (`pr_id`,
  `cost_usd`) via the second arg to each column builder — always pass that
  explicit snake_case name, don't rely on inference.

## Development workflow

Every non-trivial task (human or AI-assisted) in this repo follows the same
five phases — this isn't tooling, just the expected shape of a session:

1. **Initiation** — read the relevant `AGENTS.md`(s) and the touched
   package's `INSIGHTS.md` (see `engineering-insights` skill) before writing
   anything, so prior gotchas/decisions aren't rediscovered from scratch.
2. **Planning** — for anything beyond a trivial fix, sketch the approach
   (file paths, contracts touched, open questions) and resolve ambiguity
   with the user before touching code.
3. **Implementation** — make the change, following each touched package's
   own conventions (see the matching best-practices skill: Fastify/Drizzle/
   Zod/React/etc.) rather than copying the nearest adjacent pattern
   uncritically.
4. **Validation** — `pnpm typecheck` + `pnpm test` in every touched package,
   plus a manual/browser check for UI-visible changes; don't call something
   done on typecheck alone.
5. **Completion** — commit (branch name as the message prefix — see "GIT"
   below), and record anything non-obvious learned back into the relevant
   `INSIGHTS.md`.

## Do-not-touch

- `*/vendor/shared/**`, `client/src/vendor/ui/**` — vendored, not authored in
  place. Edit at the sync source (see the owning package's AGENTS.md).
- `server/src/db/migrations/**` (including `meta/*_snapshot.json`) —
  generated by `drizzle-kit` (`pnpm db:generate`), never hand-write or
  hand-edit a migration file; the snapshot journal must stay in sync with
  what drizzle-kit produced or later `db:generate` runs can diverge.
- `*/pnpm-lock.yaml` — each package has its own lockfile (no shared
  workspace lockfile); regenerate via the package's own `pnpm install`, and
  don't hand-edit or merge-resolve a lockfile by hand.
